# Provider Execution Semantics

**Date:** 2026-09-02  
**Scope:** Defines the contract between Sanad and execution providers, and the states of a financial execution attempt.  
**Verified by:** `test_try_claim_prevents_double_execution`, `test_unknown_state_recorded_on_provider_exception`

---

## 1. Execution States

An execution attempt may be recorded through the following states. `SENT` represents dispatch; the remaining states represent execution outcomes.

| State | Meaning | Provider Called? |
|---|---|---|
| **SENT** | Request dispatched to provider | Yes |
| **EXECUTED** | Provider confirmed success | Yes |
| **REFUSED** | Sanad denied before dispatch | No |
| **UNKNOWN** | Provider was called but no definitive success/refusal result was obtained | Yes |

---

## 2. The UNKNOWN State

UNKNOWN is **not** FAILED.

- FAILED would mean: "We know the provider refused."
- UNKNOWN means: "We do not know what happened."

Sanad records UNKNOWN when the provider call raises an exception or otherwise produces no definitive success/refusal result.

**Critical invariant:** Sanad does **not** retry automatically. UNKNOWN is a stop state.

---

## 3. Idempotency and Atomic Claim

### Same Approval, Second Attempt

Sanad uses `try_claim()` to atomically mark an approval as consumed before calling the provider.

- If `try_claim()` succeeds → the approval is claimed → the provider is called.
- If `try_claim()` fails → the approval has already been consumed.
- The same approval cannot be executed twice through the gateway.

### New Approval After UNKNOWN

If a human or system creates a new approval after seeing UNKNOWN, Sanad treats it as a new transaction:

- New `approval_id`
- New `execution_id`
- A new provider-side idempotency key may therefore be generated by the provider integration.

The old idempotency identity does not protect the new approval. Sanad cannot infer whether the first provider request executed without reconciliation.

---

## 4. Reconciliation, Not Blind Retry

After UNKNOWN, the correct operational path is reconciliation before retry.

Where supported:

1. Query the provider using `find_by_execution_id(execution_id)`.
2. If the provider confirms execution → record the execution outcome.
3. If the provider confirms non-execution → a new approval may be created and executed.
4. If the provider remains unreachable → keep the execution unresolved until it can be reconciled.

Blind retry risks double execution.

---

## 5. Execution ID and Provider Idempotency

Sanad passes `execution_id` to the Provider.

The Provider integration may use this identifier for idempotency.

The current Stripe implementation maps it to:

`Idempotency-Key: sanad-{execution_id}`

This means repeated provider requests using the same execution identity can be deduplicated by Stripe according to Stripe's idempotency semantics.

Sanad itself does not rely solely on provider idempotency. It first protects the approval with `try_claim()`.

## 6. Verified Behaviors

| Behavior | Evidence |
|---|---|
| Same approval cannot execute twice | `test_try_claim_prevents_double_execution` |
| Provider exception → UNKNOWN, no automatic retry | `test_unknown_state_recorded_on_provider_exception` |
| Ledger records SENT before provider call | `Gateway.execute()` implementation |
| Atomic claim prevents duplicate approval execution | `try_claim()` in SQLite transaction |

---

## 7. Limitations

- Sanad does not automatically reconcile UNKNOWN states.
- Sanad does not perform automatic retry after UNKNOWN.
- If the provider does not support `find_by_execution_id()`, reconciliation requires another provider-specific mechanism or manual resolution.
- A new approval after UNKNOWN is a new financial transaction, not an automatic retry of the original approval.
